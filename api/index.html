    API reference¶

    Memory¶

    poincare_memory.store.memory.Memory ¶

    Memory(
    embedder=None,
    curvature=1.0,
    decay=None,
    base_depth=1.0,
    depth_step=0.5,
    inherit=0.25,
    cone_constrained=False,
    cone_k=DEFAULT_K,
    metric="shell",
    time_coef=1.0,
    depth_bias=0.0,
    clock=None,
)

    Hierarchy-aware, time-aware memory for agents and RAG.

    Each memory gets a point in the Poincaré ball. Its direction comes from the text embedding (optionally pulled toward its parent's direction); its depth (hyperbolic distance from the origin) comes from its level in the hierarchy you declare with parent=. Structural queries (subtree, ancestors, siblings, cone) and the temporal policy are geometric and explicit, and every memory can be inspected visually.

    Scoring. search ranks memories by -distance + depth_bias * depth + time_coef * log(time_weight). With metric="shell" (default) distance is the hyperbolic distance between the query and the memory after both are moved to the reference shell at base_depth: it measures semantic (angular) mismatch in hyperbolic units and is comparable across levels. With metric="hyperbolic" it is the raw distance to the memory's actual point, which strongly favours shallow, general memories (a root at depth 1 is close to everything) and is the right choice only when the embedder itself is hyperbolic (e.g. Hierarchy Transformers) or when generality is wanted. Use depth_bias to prefer specific (> 0) or general (< 0) memories explicitly.

    Thread safety. All mutating and searching methods take an internal re-entrant lock, so a Memory can be shared between threads; the embedder you pass must be safe to call from several threads if you do.

    search ¶

    search(
    query=None,
    k=5,
    mode="nearest",
    root=None,
    at_time=None,

    Rank memories by -distance + depth_bias*depth + time_coef*log(time_weight).

    mode restricts the candidates: nearest (all), subtree/children/ ancestors/siblings of root, or cone (points inside the entailment cone of root). query may be omitted for structural modes, in which case candidates are ranked by time weight and depth only. metric overrides the memory's default (see the class docstring); query_depth only matters for metric="hyperbolic" (default base_depth).

    use_index: with True (or None once :meth:build_index has been called) a nearest + shell search first takes the k * oversample closest memories from the index, then scores them exactly with the temporal policy and filters. The index is rebuilt automatically after changes.

    poincare_memory.geometry.lorentz ¶

    Lorentz (hyperboloid) model helpers.

    The hyperboloid of curvature -c is {X in R^{d+1} : <X, X>_L = -1/c, X_0 > 0} with the Lorentzian inner product <X, Y>_L = -X_0 Y_0 + sum_i X_i Y_i.

    Why it matters for retrieval: the geodesic distance is d(X, Y) = (1/sqrt(c)) arcosh(-c <X, Y>_L), a decreasing function of the Lorentzian inner product. Negating the time coordinate of every stored vector turns <X, Y>_L into an ordinary dot product, so any maximum-inner-product (dot-product) ANN index returns exact hyperbolic nearest neighbours. This is the trick used by hyperbolic RAG systems and documented by vector-database vendors; no custom metric is needed.

    HashingEmbedder dataclass ¶

    HashingEmbedder(dim=256, ngram_range=(3, 5), seed=0)

    Deterministic, dependency-free text embedder (word + character n-gram hashing).

    It is not a semantic model; it is a stable, fast stand-in that makes the library usable offline and in tests. Swap in :class:SentenceTransformerEmbedder or any callable for real semantics.

    Algorithm (stable across versions and ports): lower-case the text; tokens are [\w']+; features are "w:" + token and "c:" + ngram for character n-grams of "#" + token + "#" with lengths in ngram_range; each feature is hashed with keyed BLAKE2b (digest 8 bytes, key = 4-byte little-endian seed); index = first 4 bytes as little-endian integer mod dim; sign = +1 if the fifth byte is odd else -1; the row is L2-normalised.

    Hierarchy¶

    poincare_memory.hierarchy.sarkar ¶

    Training-free tree embedding by Sarkar's combinatorial construction.

    Sarkar (2011) showed that any tree embeds in the hyperbolic plane with arbitrarily low distortion: put the root at the origin, place its children on a circle of hyperbolic radius tau at evenly spaced angles, then for every child move it to the origin by an isometry, place its own children on a circle around it while avoiding the direction of its parent, and move everything back. Sala, De Sa, Gu & Ré (ICML 2018) analysed the construction and extended it to higher dimensions by spreading child directions on a sphere.

    This module implements both from the papers. Larger tau lowers distortion but pushes deep nodes toward the boundary; :func:max_safe_depth tells you how deep a tree can go before floating-point projection starts compressing it.

    max_safe_depth ¶

    max_safe_depth(ball, tau, dtype=np.float64)

    Largest total hyperbolic radius representable before the ball margin clips points.

    Returns the number of tau-length steps from the origin that stay strictly inside (1 - eps) / sqrt(c).

    spread_directions ¶

    spread_directions(
    k, dim, avoid=None, seed=0, iterations=200
)

    k unit vectors in R^dim spread apart (and away from avoid if given).

    In two dimensions the angles are exact: children fill the circle evenly, with the parent's direction occupying one slot. In higher dimensions a seeded repulsion on the sphere (a Thomson-style relaxation) spreads the directions.

    sarkar_layout ¶

    sarkar_layout(
    edges,
    ball=None,
    dim=2,
    tau=1.0,
    edge_length=None,
    root=None,
    seed=0,
)

    Embed a rooted tree given as (parent, child) edges.

    Every child is placed at hyperbolic distance tau * edge_length[(parent, child)] from its parent (edge_length defaults to 1). Returns node -> point. A forest is handled by treating the listed root (or the single root) as the origin; pass a virtual root edge set if you have several roots.

    poincare_memory.hierarchy.rsgd ¶

    Poincaré embeddings trained with Riemannian SGD (Nickel & Kiela, NeurIPS 2017), in NumPy.

A Euclidean twin with the same loss is provided as a baseline for benchmarks. Implemented from the paper; no third-party code was consulted.

    Temporal policies¶

    poincare_memory.temporal.policies ¶

    Named temporal weighting policies.

    The paper describes "time-weighted embeddings" that favour recent information while keeping established knowledge reachable. Here that idea is a pluggable, testable policy that maps a memory's age (and optionally its access history or validity window) to a weight in (0, 1]. Weights enter the retrieval score as time_coef * log(weight), so a weight of 1 is neutral.

    Forms implemented from the literature: - exponential half-life (the 0.995^hours recency of Generative Agents, Park et al. 2023, is HalfLife(hours=138.3)); - Ebbinghaus forgetting exp(-t / S) with stability that grows with accesses (MemoryBank, Zhong et al. 2024); - validity windows (bi-temporal facts as in Graphiti/Zep).

    Retrieval¶

    poincare_memory.retrieval.scoring ¶

    Combining geometry and time into one retrieval score.

    combine ¶

    combine(
    distances,
    time_weights=None,
    depths=None,
    time_coef=1.0,
    depth_bias=0.0,
)

    score = -distance + depth_bias * depth + time_coef * log(time_weight).

    Larger is better. depth_bias > 0 prefers specific (deep) memories, < 0 prefers general ones; time_coef scales how strongly the temporal policy counts (1.0 means a half-life halving of the weight costs ln 2 in score, the same as moving ln 2 ≈ 0.69 further away in the ball).

    poincare_memory.retrieval.cones ¶

    Hyperbolic entailment cones (Ganea, Bécigneul & Hofmann, ICML 2018).

    Every point x in the ball (outside a small central region of radius K) owns a geodesically convex cone opening toward the boundary. "y lies in the cone of x" is the geometric form of "x entails / is more general than y". With depth encoded by the norm, cones give ancestor and descendant queries that plain nearest-neighbour search cannot express.

    Formulas (unit ball; points are scaled by sqrt(c) first): half-aperture psi(x) = arcsin(K (1 - ||x||^2) / ||x||) angle at x Xi(x, y) = arccos( ((1 + ||x||^2) - ||x||^2 (1 + ||y||^2)) / (||x|| ||x - y|| sqrt(1 + ||x||^2 ||y||^2 - 2)) ) energy E(x, y) = max(0, Xi(x, y) - psi(x)) (0 means y is inside the cone)

    cone_energy ¶

    cone_energy(x, y, ball, K=DEFAULT_K)

    max(0, Xi(x, y) - psi(x)); zero when y is inside the entailment cone of x.

    Index¶

    poincare_memory.index ¶

    Nearest-neighbour indexes for the reference-shell metric.

    Semantic search in :class:~poincare_memory.Memory compares the query with every memory on the root shell. For large stores that comparison is offloaded to a maximum-inner-product index: shell points are mapped to the Lorentz model and their time coordinate negated (:func:~poincare_memory.geometry.to_mips_vectors), after which the largest dot products are exactly the hyperbolic nearest neighbours. Two backends:

    • numpy: exact, vectorised, fine to a few hundred thousand points;
    • faiss: IndexHNSWFlat with inner-product metric (pip install poincare-memory[ann]), approximate, for millions of points.

    Visualisation¶

    poincare_memory.viz.export ¶

    Export a memory as JSON / NetworkX and project points to the 2-D disk for drawing.

    disk_coordinates ¶

    disk_coordinates(points, ball)

    2-D Poincaré-disk coordinates for drawing.

    In 2-D the points are returned unchanged (scaled to the unit disk). In higher dimensions the directions are reduced with an uncentred SVD of the tangent vectors at the origin (so the origin stays the origin) and every point keeps its exact hyperbolic depth; angles are approximate, depths are not.

    structural_coordinates ¶

    structural_coordinates(memory)

    2-D disk coordinates for inspection: angles from the hierarchy, radii from the true depths.

    Every memory keeps its exact hyperbolic distance from the origin (the paper's depth coordinate); its angle comes from a radial tree layout in which each subtree owns an angular wedge proportional to its number of leaves, so siblings spread evenly and subtrees do not overlap. This is a drawing, not an isometric embedding: use the real points for distances.
